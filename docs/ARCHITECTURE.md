## 1. アーキテクチャ概要

### 1.1 設計方針

**Google Sheets主体アーキテクチャ**

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Django ATS                                   │
│                        (Webアプリケーション)                          │
│                                                                      │
│  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐        │
│  │ 認証・セッション │  │ キャッシュ層   │  │ ビジネスロジック│        │
│  │ (PostgreSQL)   │  │ (Redis)       │  │                │        │
│  └────────────────┘  └────────────────┘  └────────────────┘        │
└─────────────────────────────────────────────────────────────────────┘
                                 ↕ Google Sheets API
┌─────────────────────────────────────────────────────────────────────┐
│                    Google Sheets (データ層)                          │
│                                                                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐              │
│  │ 会社A専用     │  │ 会社B専用     │  │ 会社C専用     │   × 100社   │
│  │ スプレッドシート│  │ スプレッドシート│  │ スプレッドシート│              │
│  └──────────────┘  └──────────────┘  └──────────────┘              │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 なぜGoogle Sheets主体か

| 理由 | 詳細 |
|------|------|
| **顧客の透明性** | 顧客が直接データを確認・ダウンロード可能 |
| **Excel互換** | 多くのユーザーが使い慣れた操作感 |
| **共有の容易さ** | リンク共有で社内展開可能 |
| **バックアップ** | Googleが自動保存 |

## 3. API制約と対策

### 3.1 Google Sheets API制限

| 制約 | 値 | 対策 |
|------|-----|------|
| 読み取り | 300リクエスト/分/プロジェクト | バッチ読み取り + キャッシュ |
| 書き込み | 300リクエスト/分/プロジェクト | バッチ書き込み |
| セル数上限 | 1,000万セル/シート | 十分 |

### 3.2 キャッシュ戦略

| データ種別 | キャッシュTTL | 更新トリガー |
|-----------|-------------|-------------|
| 一覧表示 | 5分 | ページリロード |
| 詳細表示 | 1分 | 編集保存時 |
| ダッシュボード統計 | 10分 | 手動更新ボタン |
| マスタデータ | 30分 | 設定変更時 |

### 3.3 バッチ処理

```python
# ❌ 悪い例: 4回のAPI呼び出し
candidates = sheet.get('候補者!A:Z')
applications = sheet.get('応募!A:Z')
interviews = sheet.get('面接!A:Z')
jobs = sheet.get('求人!A:Z')

# ✅ 良い例: 1回のAPI呼び出し
all_data = sheet.batch_get([
    '候補者!A:Z',
    '応募!A:Z',
    '面接!A:Z',
    '求人!A:Z'
])
```

## 4. スケーリング戦略

### 4.1 フェーズ別構成

| フェーズ | 企業数 | 構成 | 月額コスト |
|---------|--------|------|-----------|
| Phase 1 | 5-10社 | 単一GCPプロジェクト | $0-7 |
| Phase 2 | 100社 | 単一GCPプロジェクト + キャッシュ強化 | $50-100 |
| Phase 3 | 2,000社 | 複数GCPプロジェクト | $500-1,500 |

### 4.2 100社対応の具体策

```
【同時アクセス試算】
100社 × 5人/社 = 500ユーザー
同時アクティブ率: 10% = 50人
リクエスト/秒: 20-30

【対策】
1. キャッシュ活用（読み取りの80%をキャッシュから）
2. バッチAPI呼び出し（4回→1回に削減）
3. 書き込みキュー（即時性不要な処理を非同期化）
```

### 4.3 2,000社対応

```
【GCPプロジェクト分散】
プロジェクトA: テナント 1-500
プロジェクトB: テナント 501-1,000
プロジェクトC: テナント 1,001-1,500
プロジェクトD: テナント 1,501-2,000

各プロジェクト: 300リクエスト/分
合計: 1,200リクエスト/分 対応可能
```

## 5. セキュリティ設計

### 5.1 認証・認可

| 層 | 方式 |
|----|------|
| ユーザー認証 | Django Allauth（メール+パスワード） |
| セッション管理 | Django Session + Redis |
| API認証 | Google Service Account |
| 権限制御 | ロールベースアクセス制御（RBAC） |

### 5.2 テナント分離

```python
# 全ビューで適用
class TenantQuerysetMixin:
    def get_queryset(self):
        return super().get_queryset().filter(tenant=self.request.tenant)
```

### 5.3 スプレッドシートアクセス制御

| ロール | アクセス権限 |
|--------|------------|
| SYSTEM_ADMIN | 全テナントのシート |
| CONSULTANT | 担当テナントのシート |
| CLIENT_ADMIN | 自社シートのみ |
| その他 | 自社シートのみ（読み取り中心） |

## 6. 監査ログ設計

### 6.1 記録対象

| イベント | 記録内容 |
|---------|---------|
| ログイン/ログアウト | ユーザー、日時、IPアドレス |
| データ変更 | 変更者、変更内容、変更前後の値 |
| 権限変更 | 変更者、対象ユーザー、変更内容 |
| エクスポート | 実行者、対象データ、日時 |

### 6.2 ログ保存先

```
PostgreSQL（メタデータDB）
├── audit_logs テーブル
│   ├── id (UUID)
│   ├── tenant_id
│   ├── user_id
│   ├── action (login/logout/create/update/delete/export)
│   ├── target_type (candidate/application/interview/...)
│   ├── target_id
│   ├── changes (JSONB)
│   ├── ip_address
│   └── created_at
└── login_history テーブル
    ├── id (UUID)
    ├── user_id
    ├── success (boolean)
    ├── ip_address
    ├── user_agent
    └── created_at
```
